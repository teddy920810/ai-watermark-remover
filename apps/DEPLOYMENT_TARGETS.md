# Independent web deployment targets

CI uses `build-target.mjs ci-changes BASE HEAD` to complement full regression with both Site and App compilation; Worker remains selected by its actual dependencies. Public `changes` and Vercel `ignore` retain production deployment selection. Every selected web artifact runs the responsive-image check on its own final HTML before staging/upload. Both mandatory contexts must pass; coverage ownership is maintained in the [test guide](../docs/TESTING_GUIDE.md#ci-全量检查的覆盖分工). Local combined build commands remain available and unchanged.

An explicit redeployment whose previous and current Git SHAs are identical must still build: production environment variables may have changed. The `ignore` decision returns Vercel's build status (exit 1) for App and Site in this case. Ordinary commits continue to use the target change classifier. This does not bypass verification, install, build, artifact validation or deployment acceptance. Changing environment variables alone does not update an already running deployment; verify the replacement deployment and its runtime policy.

Current ownership is tracked in [current architecture](../docs/CURRENT_ARCHITECTURE.md), verification gates in [the test guide](../docs/TESTING_GUIDE.md), and published versions in [release records](../docs/product/RELEASE_READINESS.md). Earlier planning statements describe their historical baseline. This document specifies the selected topology and does not claim production or DNS acceptance for local changes.

The canonical content and source files remain in `src/`. `apps/site/src` and `apps/app/src` are route-discovery containers, not copies of CMS content. The build selects entrypoints through Astro's documented `srcDir` and `injectRoute` APIs before bundling; it never removes unwanted functions after building.

Route ownership and privacy are separate: exact `/pricing` is public, indexable request-rendered HTML owned by App, excluded from the SEO proxy. `/pricing/unknown` and other unknown SEO URLs still reach Site's real 404. Site lists Pricing in navigation and sitemap without importing server payment configuration; `/app/credits` remains private/noindex with checkout, orders and recovery. The shared route policy is `src/lib/contracts/route-policy.mjs`.

| Target | Command from repository root | Durable artifact | Vercel Root Directory |
| --- | --- | --- | --- |
| SEO | `node scripts/build-target.mjs site` | `dist-target/site/` (static only) | `apps/site` |
| App/API and same-origin SEO proxy | `node scripts/build-target.mjs app` | `dist-target/app/.vercel/output/` | `apps/app` |
| Worker artifact verification | `node scripts/build-target.mjs worker` | `dist-target/worker/` (seven-file Docker context) | Not a Vercel project |

The production topology keeps the existing `ai-watermark-remover` Vercel project, its production domain, its existing authentication secret and its other server credentials. That project builds the App target and also provides the public routing boundary. A separate `ai-watermark-site` project builds static SEO pages. The original App project's non-secret build setting `APP_SITE_ORIGIN` is `https://ai-watermark-site.vercel.app`, the Site project's verified fixed production alias. The Site project uses official Standard Protection so that this production alias serves its public static content while preview and unique deployment URLs remain protected. Do not disable protection for automation or change the original App project's protection settings. The selected topology does not configure `content.watermarkgemini.com` and requires no additional DNS record; its unused Vercel project-domain binding was removed on 2026-10-25. Keep the active Site project and its fixed production alias. App and SEO remain independently deployable through their separate build targets and target-specific ignored build steps; a content subdomain is not part of that separation. The public domain does not move and no authentication secret is copied from a local checkout. The former `ai-watermark-app` verification project was deleted on 2026-10-25; this does not retire the active `apps/app` source target.

When `APP_SITE_ORIGIN` is configured, the build adds a literal external rewrite at the start of App Build Output routes, ahead of Astro's filesystem and 404 catch-all. It matches public pages and SEO assets; `/api`, `/app`, `/auth`, `/_app-assets` and Astro internal endpoints remain local. The original App function and resource routes are retained. HTTPS origin validation rejects the canonical public origin, the Vercel deployment/production origins and an explicitly supplied `APP_ORIGIN` as SEO upstreams, preventing a direct recursive rewrite. The static upstream must itself remain the Site target and must not proxy back to App. Without `APP_SITE_ORIGIN`, an App build remains a standalone verification artifact.




The local third batch retires historical App/Site chunk manifests, the bounded remote downloader and the original /_astro proxy after the owner confirmed there are no real production users. Builds include current target assets only and no longer fetch old deployments. This is local source preparation, not a deployment or deletion of remote artifacts.

For the two Vercel Git projects, enable **Include source files outside of the Root Directory in the Build Step**. Their local `vercel.json` files select the target and the target-specific ignored build step. The build script also stages the site into `apps/site/dist` and the complete App Build Output into `apps/app/.vercel/output`. These generated folders must not be committed. A manual repository-root CLI deployment must explicitly select its target config with `--local-config`; the original root `vercel.json` remains the combined deployment for compatibility.

The App adapter currently writes `.vercel/output` under the repository root as a temporary staging directory. It is copied whole, without deleting functions, into the App artifact and deployment root. Site and App final artifacts never overwrite each other. Do not run a target build concurrently with a combined Astro build in the same checkout: Astro's generated type directory and the Vercel adapter's staging directory are shared.

Site's responsive-image results use the repository-root `.vercel/cache/optimized-images/`, which Vercel's native build cache preserves before install/build, including the current Other preset and monorepo root. No Vercel settings or new storage service are required; the cache never enters static output. GitHub restores/saves only this directory for Site and full/ui verification, using pinned official cache actions and Node/platform/version-scoped keys; hits do not skip any checks. Separate cache steps expose transfer time. A same-SHA Site job rerun replaces its same-named artifact only after a fresh validated build. See the [developer cache contract](../docs/DEVELOPER_GUIDE.md#内容模型) and [Vercel's cache contract](https://vercel.com/docs/deployments/troubleshoot-a-build#what-is-cached). Previous local experiment data under `output/cache/optimized-images` is disposable and no longer read.

Every web target prepares its approved generated input/output directories once in the `astro:config:setup` integration hook before route injection. Reading configuration or planning/dispatching a target build does not clear directories. App also clears the adapter's temporary `.vercel/output`, preserving `.vercel/project.json`; staging recreates only the selected target's deployment output. Symlink or junction ancestors are rejected before recursive removal. Only current generated assets enter the artifact; earlier local or deployed chunks are not carried forward.

Both web targets use separate empty environment directories and remove server credential variables from their build subprocesses. The site target has no adapter; its module-boundary plugin rejects imports of project authentication, Provider, database or processing implementations. App uses `apps/app/astro.config.mjs`, which does not load the SEO Markdown pipeline. Its content collection loads only shared site identity, excluding Blog/landing publication records. Compiled assets use `/_site-assets/` and `/_app-assets/`; the App public directory contains only brand assets, the image fallback and assets actually referenced by workspace styles. Server credentials are required only when App functions run.

Site retains the existing security headers and legacy URL redirects. App retains the security headers and applies private caching and noindex only to its private routes. It has no global noindex header because that would also mark proxied SEO pages as noindex. Focused regression tests require the inherited values to stay aligned with the root combined-deployment configuration.


The App-to-Site proxy preserves paths and upstream status codes, including SEO 404s. Static route transforms strip request Cookie/Authorization before SEO and strip response Set-Cookie from SEO. App authentication cookies remain on the original public same origin. Production verification must check the proxy response headers, an unknown SEO path, local App/API routes and the existing OAuth session before the launch is accepted.

`.github/workflows/build-targets.yml` uses one change classifier for Site, App and Worker. Blog/landing content selects Site; a Worker entry or Docker change selects Worker; shared processing runtime changes select App and Worker; dependencies or the shared build entry select all three. It only builds and uploads the selected artifacts and uses no deployment credentials. Worker validation invokes the real bundler and checks the complete seven-file upload allowlist and bundle manifest. `npm run build:worker` retains its standalone local bundle and temporary-context behavior. Container image building, deployment and execution verification remain separate steps in [Worker deployment](../docs/product/WORKER_DEPLOYMENT.md).

Vercel Git integration performs target-specific web deployments with `ignoreCommand`. The stable required `CI / verify` selects the documented verification mode, and `Required target artifacts` must pass for every selected target. Unknown/mixed/high-risk verification retains audit, coverage thresholds, lint, type/build and browser checks. Content verification avoids the unrelated combined App build; its selected Site artifact is built once per workflow SHA. Vercel still builds its own production-environment artifact from the exact merged SHA. PR merge refs, head refs and squash-main refs are different identities: this phase does not reuse a PR artifact for main, deploy Windows output to Linux, or claim CI output and Vercel output are byte-identical.

Repository-root `.vercelignore` excludes private credentials, local tools, evidence, generated target output, image derivatives and test sidecars while retaining all source, original media, content and current deployment manifests. It controls CLI source uploads, not tracked Git history or the existing Git integration's source checkout. Independent Vercel project roots and the Worker seven-file allowlist remain separate boundaries. No file is deleted by ignore changes; exact deployment identity, real aliases and production behavior remain separate release evidence.

Native packages in App Build Output match the build machine. Use Vercel's source build or the Ubuntu CI artifact for Linux deployment; a locally verified Windows artifact is not a portable Linux function bundle.
