# Independent web deployment targets

Current implementation and release gates are tracked in [IMPLEMENTATION_TODO](../docs/product/IMPLEMENTATION_TODO.md). Earlier planning statements describe the research baseline, not the current repository state; this document specifies the selected launch topology and does not claim that deployment or DNS verification has finished.

The canonical content and source files remain in `src/`. `apps/site/src` and `apps/app/src` are route-discovery containers, not copies of CMS content. The build selects entrypoints through Astro's documented `srcDir` and `injectRoute` APIs before bundling; it never removes unwanted functions after building.

| Target | Command from repository root | Durable artifact | Vercel Root Directory |
| --- | --- | --- | --- |
| SEO | `node scripts/build-target.mjs site` | `dist-target/site/` (static only) | `apps/site` |
| App/API and launch gateway | `node scripts/build-target.mjs app` | `dist-target/app/.vercel/output/` | `apps/app` |
| Optional separate gateway | render literal config; no product build | `apps/gateway/vercel.json` | `apps/gateway` |

The first production launch keeps the existing `ai-watermark-remover` Vercel project, its production domain, its existing authentication secret and its other server credentials. That project builds the App target and also provides the public routing boundary. A separate `ai-watermark-site` project builds static SEO pages. Set the original App project's non-secret build setting `APP_SITE_ORIGIN` to the Site project's verified fixed production `vercel.app` alias after deployment. The new Site project uses official Standard Protection so that this production alias serves its public static content while preview and unique deployment URLs remain protected. Do not disable protection for automation or change the original App project's protection settings. This launch does not require DNS access; a custom content subdomain remains optional for later. App and SEO remain independently deployable; the public domain does not move and no authentication secret is copied from a local checkout. The optional `ai-watermark-app` project is a verification environment, without production secrets.

When `APP_SITE_ORIGIN` is configured, the build adds a literal external rewrite at the start of App Build Output routes, ahead of Astro's filesystem and 404 catch-all. It matches public pages and SEO assets; `/api`, `/app`, `/auth`, `/_app-assets` and Astro internal endpoints remain local. The original App function and resource routes are retained. HTTPS origin validation rejects the canonical public origin, the Vercel deployment/production origins and an explicitly supplied `APP_ORIGIN` as SEO upstreams, preventing a direct recursive rewrite. The static upstream must itself remain the Site target and must not proxy back to App. Without `APP_SITE_ORIGIN`, an App build remains a standalone verification artifact.

For the first split, configure `LEGACY_ASSET_ORIGIN` as the original combined deployment's immutable origin. The selected release input is `https://ai-watermark-remover-py1qfsov7-shiyaos-projects-b1e333f0.vercel.app`. A higher-priority GET/HEAD-only route preserves original `/_astro/*` static resources for already-open pages and cached old HTML. It strips request Cookie/Authorization and response Set-Cookie, rejects traversal paths and cannot target the public origin, current App origins or current Site origin. It never forwards App, API, authentication, SEO or new asset-prefix paths to the old application. Keep this immutable deployment available while those old pages may reference its assets. The release checklist must link the five legacy assets' anonymous-response and SHA-256 evidence; rendering a route alone is not that evidence.

Later independent App/Site releases must carry prior public hashed assets into the current static build input under their own `/_app-assets/` or `/_site-assets/` prefix, preserving the current file whenever the same name exists. Merge only public static resources, never previous HTML, API routes, functions, private uploads or results. Before the next independent release, verify both the new hashes and the prior hashes referenced by a retained/open page, plus an unknown SEO path's real 404. This asset-retention build step is a gate for that future release; the initial `LEGACY_ASSET_ORIGIN` route does not automatically preserve every future App/Site version. No cross-origin 404 fallback is claimed or generated, and an unset `PREVIOUS_APP_ORIGIN` or `PREVIOUS_SITE_ORIGIN` is not treated as an implemented recovery mechanism.

For the two Vercel Git projects, enable **Include source files outside of the Root Directory in the Build Step**. Their local `vercel.json` files select the target and the target-specific ignored build step. The build script also stages the site into `apps/site/dist` and the complete App Build Output into `apps/app/.vercel/output`. These generated folders must not be committed. A manual repository-root CLI deployment must explicitly select its target config with `--local-config`; the original root `vercel.json` remains the combined deployment for compatibility.

The App adapter currently writes `.vercel/output` under the repository root as a temporary staging directory. It is copied whole, without deleting functions, into the App artifact and deployment root. Site and App final artifacts never overwrite each other. Do not run a target build concurrently with a combined Astro build in the same checkout: Astro's generated type directory and the Vercel adapter's staging directory are shared.

Both web targets use separate empty environment directories and remove server credential variables from their build subprocesses. The site target has no adapter; its module-boundary plugin rejects imports of project authentication, Provider, database or processing implementations. App uses `apps/app/astro.config.mjs`, which does not load the SEO Markdown pipeline. Its content collection loads only shared site identity, excluding Blog/landing publication records. Compiled assets use `/_site-assets/` and `/_app-assets/`; the App public directory contains only brand assets, the image fallback and assets actually referenced by workspace styles. Server credentials are required only when App functions run.

Site retains the existing security headers and legacy URL redirects. App retains the security headers and applies private caching and noindex only to its private routes. It has no global noindex header because that would also mark proxied SEO pages as noindex. The optional separate gateway also carries the existing global security headers. Focused regression tests require the inherited values to stay aligned with the root combined-deployment configuration.

For a future three-project topology, `apps/gateway/vercel.template.json` is a reference template. The committed `apps/gateway/vercel.json` returns a safe 503 until a configured literal version replaces it. Set the non-secret `SITE_ORIGIN` and `APP_ORIGIN` to distinct upstream HTTPS deployment origins and run `node scripts/build-target.mjs gateway`. The command requires both origins and prints the complete literal configuration for review; it does not deploy or overwrite files. Save that output as the gateway project's `vercel.json` before deploying the optional separate gateway. Do not deploy the placeholder template. The public origin comes from the shared site identity settings.

Both routing topologies preserve paths and upstream status codes, including SEO 404s. Static route transforms strip request Cookie/Authorization before SEO and strip response Set-Cookie from SEO. App authentication cookies remain on the original public same origin. Production verification must check the proxy response headers, an unknown SEO path, local App/API routes and the existing OAuth session before the launch is accepted.

`.github/workflows/build-targets.yml` only builds and uploads the affected target artifacts; it uses no deployment credentials. Vercel Git integration performs target-specific deployments with `ignoreCommand`. The existing required `CI / verify` remains unchanged and remains the merge gate. Targeted deployment selection does not waive that gate.

Native packages in App Build Output match the build machine. Use Vercel's source build or the Ubuntu CI artifact for Linux deployment; a locally verified Windows artifact is not a portable Linux function bundle.
