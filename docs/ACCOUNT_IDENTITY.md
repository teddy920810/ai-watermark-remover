# Canonical Google account identity

Release progress is tracked in [IMPLEMENTATION_TODO](product/IMPLEMENTATION_TODO.md). Apply `007_google_account_owners.sql` before deploying the new authentication mapping. This document does not assert that the migration or production verification has completed.

The installed Better Auth configuration has no persistent authentication database. Its signed/encrypted stateless session is valid, but its in-memory adapter can generate a different user ID after a cold start and another OAuth login. The existing email identity table is unique by email, so using the new transient ID directly can cause a uniqueness error and split account ownership.

`google_account_owners` records the permanent association between a verified Google subject and the existing business owner ID. Migration 007 inserts only associations for unique verified Google profiles already matching a legacy email identity; ambiguous profiles remain unbound. It does not update balances, free uses, ledgers, task admissions, legacy IDs or R2 objects. An existing account is never reassigned merely because another subject presents its email.

On OAuth callbacks, the existing provider mapper first saves the Google profile, then resolves its canonical association. The supported `databaseHooks.user.create.before` hook assigns that owner ID before the SDK adapter creates the user. An offline test against the installed SDK proves the same ID across two fresh memory adapters. Returning an ID from `mapProfileToUser` is ineffective because the SDK removes it; marking a custom profile field `input:false` also causes it to be filtered. The implementation uses neither workaround and preserves the provider mapper's `{}` return.

The business `getSession` wrapper always authenticates through Better Auth first and requires `emailVerified === true`. A session already containing a canonical ID resolves directly through its subject association. For an older signed session with a transient ID, compatibility is limited to a verified Gmail address and an already-migrated, unique Google profile and legacy owner association. It is a read-only lookup and lets a current compatible session continue without signing in again. An unverified session, ambiguity or missing association fails closed. An older non-Gmail transient session needs a fresh OAuth sign-in; it is not silently linked by email. Google documents `sub` as the stable identifier and distinguishes authoritative Gmail addresses from verified third-party email addresses: [Google token verification](https://developers.google.com/identity/gsi/web/guides/verify-google-id-token).

All existing and v1 business APIs import this same `getSession`, so free uses, history, uploads, jobs and processing credits use the original canonical owner. The wrapper normalizes both `user.id` and `session.userId` and uses the binding's last verified email. Existing cookies and the authentication secret are preserved. The generic SDK `/api/auth/get-session` response may still display an older cookie's transient ID until its next OAuth sign-in; clients must not use that ID to authorize ownership.

Do not repair a conflict by dropping the email index, overwriting another owner's email row, moving task keys or deleting financial history. Investigate conflicting subject/email associations explicitly. Administrator grants and revocations continue to resolve the canonical legacy identity by email and retain their audit records.

Relevant installed SDK paths: `better-auth/dist/oauth2/link-account.mjs`, `db/with-hooks.mjs`, `db/schema.mjs`, `api/routes/session.mjs`, and the Google provider implementation. The public create-hook contract is documented in [Better Auth database hooks](https://better-auth.com/docs/concepts/database#database-hooks).
