### Pricing 的实现归属

`/pricing` 是网站的公开商业页面。为保留现有“首屏即有真实套餐”的行为，推荐由现有 App 服务端构建目标请求时渲染，沿用 `getPaymentConfig → publicPaymentCatalog`；Site 提供入口和 sitemap 登记。URL 公共/私有与内部由哪个构建目标提供服务，应分别定义。

SEO 内容页继续静态生成。Pricing 作为读取实时目录的公开功能页，不在静态 Site 中复制售价，也不让 Site 导入支付服务端配置。它的初始 HTML 与结算页/API使用同一公开目录；完整配置不序列化给浏览器。初期公开页面使用 `no-store` 保证目录新鲜，同时保留可索引 canonical。

`/app/credits` 的旧 URL、`returnTo`、`#orders` 和当前付款恢复存储继续有效，因此不做整页重定向。公开 Pricing 链接改为 `/pricing`；选套餐后通过经过验证的 SKU 进入现有结算页面。SKU 仅代表选择，不携带可信金额；已有 activeAttempt 的订单、SKU 和 requestKey 优先于新 URL 参数。

## 6. 阶段交付与统一验收格式

每阶段形成一个独立可审阅工作包：范围/不变量、目标红测、最小diff、定向绿测、所选唯一风险门禁、用户场景验收、回退办法与未完成项。阶段通过后才进入依赖它的下一阶段；不把多个阶段夹带进一次大改。

| 门禁 | 记录方式 |
| --- | --- |
| 本地代码 | 红测、绿测、一次所选风险门禁；首失败和等价补验分别保留 |
| 用户场景 | 桌面/手机正向与负向；处理操作核对输出、归属、费用与恢复 |
| Git/PR | 明确本地或main交付目标；提交范围清楚，合并前required CI全量成功 |
| 部署 | Site/App/Worker逐个核对适用目标、产物与SHA，不能互相替代 |
| 域名/OAuth | 仅直接变动或业务链路变化时执行对应真实验收，其他标not applicable |
| 生产功能 | 公共只读检查与认证/Provider/真实付款分别报告；缺少必需真实验证时标pending/blocked |

### 更新责任与触发时点

- **每次变更：**执行者（包含Codex）完成受影响规范和测试同步；复核者确认“更新了什么”和“不需要更新什么”的依据。关键合同没有同步时，不标记该阶段完成。
- **每次发布：**记录本次版本、目标、检查和未验收项；核对生产实际绑定版本，确认D盘基线可复现。复用PR、CI、部署信息与证据链接，不另抄一份实时状态表。
- **每阶段收尾：**复核当前规范与已实现状态、临时适配清单、未归并改动和工作树；将历史结果归档，不持续堆进现行教程。
- **每月轻量复核：**查看未完成/逾期兼容项、有效文档冲突和维护目录偏离。实际代码变化时再运行匹配检查，不定期无差别重跑全量测试。本轮不创建定时任务。

产品负责人确认目标和例外；改动执行者负责同步；复核者确认语义和证据。角色可以由同一人的不同审阅步骤或独立审查承担，不要求新增组织或管理系统。

### 文档状态和完成标准

现有文档按“当前规范 / 待确认设计 / 已接受设计决定 / 发布记录 / 历史验收 / 可执行模板”明确分类。当前规范只描述已实现且应遵守的行为；计划和历史不能当成当前能力。重要规范注明适用范围、责任角色和核对依据；具体实现版本优先从Git/发布记录引用，不手填一个不断过期的当前SHA。

阶段只有在代码/内容、合同、测试、必要说明、兼容/回退及适用验收均结清后才能关闭。首失败、补验、pending/blocked和not applicable分别记录；实际生产验收缺失时不以代码检查代替。人工可以发现并修正规则例外，但例外要有原因、影响范围和退出条件。

自动检查只承诺能验证的约束，不能声称理解全部文档语义或阻止任意外部编辑。AGENTS约束协作、仓库检查验证合同、合并/发布设置强制门禁、人工复核负责语义与实际场景，四者共同形成维护闭环。

### 规则启用顺序

1. P0先把D基线与当前任务目录归一，建立开工/收尾核对。
2. P1落地AGENTS硬规则、当前文档索引、变更影响说明、路由/目标合同检查，并核实受控合并与CMS发布链。
3. P3/P5逐步启用公共入口与单/双图规则；未迁旧实现列入有退出阶段的兼容清单，不能把待实施规范伪装成当前检查已全部通过。
4. 后续每阶段按同一闭环维护；遇到新例外更新权威规则和对应检查，避免继续叠加临时分支。
